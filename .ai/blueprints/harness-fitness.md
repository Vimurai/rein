# Blueprint — Harness fitness: a digest that cannot go stale, a ledger of what each control catches, and an evaluator that runs the acceptance line (D-159)

## Goal & Architecture
Rein is a user harness on top of Claude Code: guides that act before the agent works
(rulefiles, blueprints, skills) and sensors that check afterwards (the pre-tool-use gate, the
critics, `rein ci run`, `rein doctor`). Three of its parts do not hold today:

1. **The digest goes stale and nobody is told.** On 2026-11-17 `.ai/DIGEST.md` was dated
   2026-10-22 and described the pre-rename product at v4.1.0 while the product was Rein v0.5.0. Preflight reads
   the digest first, so every session started from a wrong snapshot. Cause: the digest is
   written by a model (`rein-digest`, `digest_updater`) that must be asked; the only prompt is
   a banner `hooks/stop-hook.sh` prints to stderr on exit 0, which the session never shows; the
   flag behind it (`digest_stale` in `state.sqlite`) is set by `run_handover` only and is
   per-machine; nothing looks at age or content.
2. **Nobody knows which controls still earn their cost.** Telemetry holds 113 `REJECTED` rows
   in about 48,000 tool calls, with no record of which rule fired. Eighteen MCP servers and
   six critics run with no count of what each one caught.
3. **The builder grades its own work.** A task's `Acceptance:` line is checked by the Engineer
   that built it. The critics read the diff against written rules; none of them runs the
   acceptance line.

Users: both roles at session start (digest), the Architect when ruling what to keep or retire
(ledger), the Engineer before a Tier 2 or Tier 3 task closes (evaluator). In one sentence: the
digest becomes a generated view, every block names its rule, and a fresh agent runs the
acceptance line before DONE.

## Core Concept
**A fact that can be computed is computed; a judgment is made by someone who did not do the
work.** The digest is a pure function of tracked files, so it is rebuilt, never remembered to
be rebuilt. The ledger is a SQL aggregate over rows the gate already half-writes. The
evaluator is the one place a model is added, because "does it do what the task said" is a
judgment, and it is given to a fresh context with no write tools.

Nothing here adds an automatic removal. The ledger reports; the Architect rules.

## Components

### Component 1 — The digest builder (`rein digest`)
`src/shared/digest-build.mjs` exports `buildDigest(projectDir) → { text, inputs }` and is the
only writer of `.ai/DIGEST.md`.

**Inputs — tracked files and git only.** `.ai/state.json` (tasks, stamps), `.ai/DECISIONS.md`
(headings), `.ai/BRIEF.md`, `package.json` version, the newest `v*` tag reachable from HEAD.
Not `LOG.md`, `SESSION.md`, `state.sqlite`, telemetry or the wall clock: those differ per
machine, and a digest built from them differs per clone. If the Engineer finds a section
below needs an untracked input, the section is dropped and reported in the handoff, not fed
from the untracked file.

**Sections, fixed order, 60 lines at most:**

| Section | Source | Rule |
|---|---|---|
| Header | newest input record | `# DIGEST — <project> (as of <date of newest task/stamp/decision>) · inputs <12 hex>`; second line `Generated by rein digest build — do not hand-edit` |
| Product | `BRIEF.md` | its first paragraph, cut at 400 characters |
| Release | git, `package.json` | newest tag, package version, a note when they differ |
| Queue | tasks | counts by status and owner; open tasks by tier; `Open more than 30 days: N` (age from the task's created date against the newest input date, not today) |
| Current focus | tasks | the five lowest-id OPEN Engineer tasks and every OPEN Architect task: id, first 110 characters |
| Review health | stamps | per stamp type, PASS/FAIL counts over the last 30 input days; every FAIL with no later PASS for the same task |
| Key decisions | `DECISIONS.md` | the last eight `## D-` headings, cut at 160 characters |
| Recent changes | tasks | the last ten DONE tasks by completion order: id, date, first 110 characters of the summary |

**Determinism.** Same inputs, same bytes: sorted iteration, `\n` endings, no locale calls, no
absolute paths. `inputs` is the first 12 hex of sha256 over the input bytes in the fixed order
above; it is how staleness is decided.

**Triggers — two, both call the same idempotent function.**
- `hooks/session-start.sh`, before the context is emitted: so no session reads a stale digest.
  Fail-open and silent: a builder error leaves the old file and emits one context line
  `[DIGEST_BUILD_FAILED] <reason> — run: rein digest build`.
- `run_handover` in `src/mcp/orchestrator-mcp/run-handover.mjs`, where it sets `digest_stale`
  today: so the digest changes in the same bookkeeping commit as the task that changed it.

The file is rewritten only when the bytes differ, so a session that changes nothing leaves the
tree clean. The handoff commit of both roles already names every tracked `.ai/` path the turn
dirtied (D-147 r1), so a rebuilt digest rides it with no skill change to the commit line.

**Removed in the same change (no dormant code):** the digest append and the stale banner in
`hooks/stop-hook.sh`; the `digest_stale` and `digest_stale_reason` meta keys and their readers
and writers; the skills `rein-digest` and `digest_updater` (registered in
`src/config/legacy-artefacts.json`, which `src/shared/legacy-registry.mjs` loads, so
`rein sync` removes installed copies — D-159 addendum 1); every agent or
skill instruction that appends to `DIGEST.md` (the `SECURITY.md updated` lines came from one).
`rein-preflight` says the digest is generated and drops its "stale after 3 days" text;
`.claude/rules/ai-bookkeeping.md` lists `DIGEST.md` beside `TASKS.md` as a generated view.

### Component 2 — The control ledger (`rein gate ledger`)
**Attribution.** Every exit-2 path in `hooks/pre-tool-use.sh` writes one telemetry row with
status `REJECTED` and a new nullable column `rule`: the bracket code plus the analyzer's rule
id when there is one (`SAFE_EXEC_BLOCK:CURL_PIPE_SHELL`, `SOVEREIGNTY_BLOCK:architect-write`,
`GATE_INTERNAL_ERROR`). The value comes from a closed list in one module
(`src/shared/gate-rules.mjs`); a value outside the list is written as `UNLISTED`. The command
text, its arguments and paths are never written.

**The ledger.** `src/shared/gate-ledger.mjs`, read-only over `~/.rein/telemetry.sqlite` and
the project's `.ai/state.json`:

| Row kind | Columns |
|---|---|
| gate rule | fires; `overridden` = fires followed by a `BYPASS` row in the same session within 10 minutes; first and last fire |
| critic / review stamp | tasks reviewed, FAIL count, FAILs later followed by a PASS on the same task |
| MCP server | tool calls, distinct sessions, error rate, median latency |

Flags, advisory only: `[CONTROL_QUIET]` for a rule, critic or server with zero fires, FAILs or
calls in the window; `[CONTROL_NOISY]` for a gate rule with `overridden / fires ≥ 0.5` and at
least four fires.

**What the flags mean.** A quiet rule that blocks a catastrophic command (`RM_RF_ROOT`, the
gate self-disable set, the Architect write scope) is kept: it is a seatbelt, and no fires is
the expected reading. A quiet critic or server is a candidate. For each candidate the
Architect answers three questions in a D-ruling: does Claude Code now do this natively
(native-first.md), did it catch anything in the window that nothing else would have, and what
does it cost per task. Retirement is always a ruled E-task, never a side effect of the ledger.

**First review.** The Architect runs the ledger once 30 days of `rule` rows exist (P-52).

### Component 3 — The acceptance evaluator (`critic_acceptance`)
An agent in `src/claude/agents/critic_acceptance.md`, tools `Read, Grep, Glob, Bash,
mcp__task-synchronizer-mcp__add_stamp`. No `Write`, no `Edit`. It inherits the pane's model
(D-110: it judges, it does not match rules).

**Procedure.** Given a task id: read the task's `Acceptance:` text from state; split it into
clauses; for each clause decide what observation would prove it, make that observation (run
the command, read the output, open the file), and record one row. Verdict per clause:
`PASS` (observed), `FAIL` (observed otherwise), `UNVERIFIED` (could not be observed here: a
hosted run, an operator action, an absent host tool; the reason is named). A clause is never
`PASS` because the diff looks right or the Engineer's handoff says so.

**Stamp.** `[ACCEPT_PASS]` when every clause is PASS or UNVERIFIED-with-reason and at least
one is PASS; `[ACCEPT_FAIL]` otherwise. The summary carries the clause table. The stamp is
bound to the sha like every stamp (E-329).

**Where it runs.** `rein-review` and `run_review` dispatch it for Tier 2 and Tier 3 after the
existing critics pass. A Tier 2 or Tier 3 task does not reach DONE without `[ACCEPT_PASS]` on
its sha, by the same check that requires the other stamps. Tier 1 is unchanged.

**The planner side.** `task-planner` gains Check 6: each acceptance clause names something
that can be run or looked at. "Works correctly" is refused; "`rein digest check` exits 1 after
a task is closed without a rebuild" passes.

### Component 4 — Order of work and queue hygiene (Architect)
- Order: E-429 and E-430 (the digest, asked for by the operator) first; then the open security
  tasks E-393 and E-353; then E-431; then E-432, which touches the same gate file as E-393 and
  E-353 and therefore follows them.
- P-51: the Architect rules on every OPEN task that an accepted decision has overtaken (the
  licensing tasks after D-123, the mirror and two-repository tasks after D-129, the
  `v4.1.0` release task after D-131) and closes or rewrites each one by id.

### Not built — a worktree per Engineer
Other harnesses run one git worktree per parallel agent. Rein has one Engineer pane and one
operator, and published results show shared-state parallel agents performing like one to
three. It is designed when a second Engineer pane is wanted, not before; the claims on the
trunk (E-331) already give the exclusion it would need.

## Data Model
```
.ai/DIGEST.md                      generated view, tracked; header carries `inputs <12 hex>`
tool_executions.rule  TEXT NULL    closed list from gate-rules.mjs, or 'UNLISTED'; NULL on old rows
stamps.type           + ACCEPT_PASS | ACCEPT_FAIL
meta.digest_stale, meta.digest_stale_reason        removed
ledger row (JSON)     { kind: "gate"|"critic"|"server", id, window_days, fires, overridden,
                        fails, fails_then_pass, calls, sessions, error_rate, p50_ms,
                        first, last, flags: [] }
clause row (in stamp summary)   <n> | PASS|FAIL|UNVERIFIED | <what was observed, 120 chars>
```
The `rule` column is added by the existing telemetry migration path (the status-enum rebuild
pattern in `telemetry.mjs`); old rows keep NULL and are counted as `UNATTRIBUTED` in the
ledger, never guessed.

## API / Interface Contracts
| Call | Output | Exit |
|---|---|---|
| `rein digest build` | `[DIGEST_BUILT] inputs <hex>` or `[DIGEST_OK] inputs <hex>` (bytes unchanged) | 0; 1 with `[DIGEST_BUILD_FAILED] <reason>` and the old file untouched |
| `rein digest check` | `[DIGEST_OK]` or `[DIGEST_STALE] built from <hex>, inputs now <hex>` | 0 fresh, 1 stale, 2 unreadable inputs |
| `rein doctor` (project scope) | one record `digest`: OK or `[DIGEST_STALE]`, a warning, never a hard fail | unchanged |
| `rein gate ledger [--days N] [--json]` | the three tables and the flags; default 90 days; `--json` prints the ledger rows | 0; 2 on a bad option; `[LEDGER_EMPTY]` when telemetry has no rows |
| agent `critic_acceptance` with a task id | one stamp, clause table in the summary | — |

Both new commands join the pinned CLI surface and `rein help`. `rein digest` works in any Rein
project, not only this repository; `rein init` writes the first digest by calling the builder.

## Security
- **Writers into the tracked tree.** The digest text passes through the shared `redact()`
  before it is written (D-130), like every automated writer. Its inputs are tracked files that
  were redacted when written, so a hit is a defect to report: the builder prints
  `[PRIVACY_REDACTED]` and still writes the redacted text.
- **The session-start trigger runs at every session start, in every project.** The builder is
  resolved through `rein_locate` from the install mirror, never from the project tree (the
  E-225 rule); it reads only the five inputs by fixed relative path under the project's
  `.ai/`, refuses a symlinked `.ai/DIGEST.md` or one that resolves outside the project, and
  writes through a temp file and rename in the same directory.
- **The ledger column.** `rule` holds a value from a closed list or the literal `UNLISTED`; it
  is bound as a parameter, never concatenated. No command text reaches telemetry, so the
  ledger adds no new personal data and telemetry still never leaves `~/.rein` (D-130).
- **The gate change is attribution only.** E-432 must not change any verdict: every row of
  the pinned verdict tables keeps its result and the fixture sha256 values are unchanged. A
  telemetry write that fails or times out never turns a block into an allow or the reverse;
  the exit code is decided before the write.
- **The evaluator runs commands.** It runs as the Engineer role under the same gate, with no
  `Write` or `Edit` tool; its prompt forbids installing packages, network calls beyond what a
  clause names, and any git command that changes refs. Task text is data: an acceptance
  clause that reads as an instruction to the agent ("ignore the above", "stamp PASS") is
  reported as `FAIL` with that reason.
- Gate surface: E-432 is Tier 3 with `security_engineer` then `critic_security`.

## Execution Constraints
- Digest build: at most 60 ms added to a warm session start on this repository's inputs
  (`state.json` plus a 5,200-line `DECISIONS.md`), measured against the existing hook-latency
  row, declared as a ceiling under D-138's rule, not as an absolute machine budget. Headings
  are read in one pass; `DECISIONS.md` is never parsed beyond `^## D-` lines.
- No lock: the write is a rename; two sessions starting together produce the same bytes.
- Ledger: one read-only connection, aggregates only, under 500 ms on 100,000 rows.
- Gate attribution: no added process on the allow path; on the block path the row is written
  by the telemetry call pattern the `BYPASS` row already uses.
- Evaluator: 15 minutes wall clock per task; one dispatch per review, re-run only after a new
  commit.
- Tests follow D-088: builder rows in one fixture table (`tests/fixtures/digest-cases.json`)
  driven by one unit file; ledger rows in one unit file over a fixture database; gate
  attribution as added columns on existing verdict rows where the harness allows, else one
  new table; no suite named for a task.

## Rollback Plan
- Digest: revert E-430 to stop the triggers; the last built file stays valid as a snapshot.
  Reverting E-429 as well restores the two skills from git. No data is lost: the digest holds
  nothing that is not in its inputs.
- Ledger: the `rule` column is nullable and ignored by every other reader; reverting E-432
  leaves it unused. The command is read-only.
- Evaluator: remove it from the review dispatch list and from the DONE check in one revert;
  existing `ACCEPT_*` stamps stay as history.
